# Dokime Architecture

Declare product contracts once in `dokime-domain` and implement handlers in `dokime-runtime`. Interfaces consume the `dokime` entry library and expose the same operation contracts without redeclaration or forwarding implementations. Host-free consumers depend on `dokime-domain` directly.

Host plugin rows, contracts, cadences and document defaults belong to the definitions-only default of `plugin-host`, consumed explicitly without runtime re-exports. Application lifecycle records remain in `dokime::host`. `PluginOwner::Host` identifies embedding application catalogs, presented as Built-in.

Mutable resources register as `Arc<tokio::sync::Mutex<T>>` or `Arc<tokio::sync::RwLock<T>>`. Server owners prepare their composition before launching Dokime and acquire the activated service afterward; listeners do not register handlers. Dokime initialization validates recovered ownership, starts record capture and commits startup recovery before assembling its live handle. Harmos invokes storage reconciliation after application initialization, so that callback cannot own prerequisites of the initialized handle.

The backend owns the durable external-effect journal and execution cleanup. Plugins durably prepare owner-qualified inverses before external writes and confirm native completion timestamps. The journal retains at most one inverse per `(RecordScope, resource)`: the earliest inverse and its restoration position survive later prepares. Every prepare receives a unique confirmation ticket; coalesced tickets retain call metadata without another inverse. Each ticket retains its calling provider for confirmation ownership and evidence; cross-execution resource exclusion remains enforced. Confirming a later rollback or leaving a later prepare unconfirmed never removes the earliest inverse. A first-call rollback removes it only if no later prepare has joined it. Run cleanup closes write admission and restores each resource once in reverse first-prepare order while evidence capture stays open. Prepared/applied evidence describes each call's ticket, description and timestamps, with `restoration_ticket` naming the earliest prepare and `coalesced` identifying later tickets. Restored evidence distinguishes a call rollback (`resource_restored: false`, inverse retained) from successful resource restoration (`resource_restored: true`, earliest ticket retired); a sole first-call rollback also retires the inverse. Development storage remains v1 with clean schema breaks and no silent data reset. After plugin admission, startup restores pending inverses before interrupted executions are recovered or plugins are exposed; a missing or failed inverse refuses startup and remains pending. Read-only `RunStart` contributions capture structured execution evidence before steps through the ordinary plugin boundary. The host plugin owns native controls and inventory; the backend has no host implementation dependency.

Host telemetry belongs to `plugins/sidecars/host`, shipped as `plugin-host.dokime`; the runtime ingests it through the common plugin boundary and carries no host collector feature or dependency. OBC under `plugins/sidecars/obc` is test-only. Installer manifests select bundles only through top-level `[[plugin]]` entries with exactly one of `name` (selected release's format 2 feed) or `path` (relative to the organization pack, with no fallback to base plugin files). Repeatable `--plugin` arguments add equivalent external inputs relative to the invocation directory. The pack's `plugins/` folder is storage only: unlisted files never ship, and plugin files are not discovered or overlaid. Distribution and sidecars archives are verified against release SHA256SUMS; selected plugin members are also verified against feed digests. Bundled packages install through the ordinary plugin store at startup when absent or older; equal or newer installed versions are retained, including their settings and disabled state.
