# gRPC Plugins Design

Status: shape agreed on 2026-11-10; not implemented. Code below is the
intended shape, not landed source. Exact names and field numbers are settled
during implementation.

## The Flow

```text
Plugin (Managed | Remote)
  └─ catalog: dokime.suites, operations, streams

TestCaseTemplate ── expand (host) ──► parameter sets
parameter set ──── materialize (plugin, pure) ──► TestCase
TestCase ───────── execute (host) ──► Execution
Execution: initialize → steps → criteria → cleanup, each an operation call
```

| Stage | Owner | Notes |
| --- | --- | --- |
| Template, parameter definitions, files, document | Plugin catalog | `dokime.suites` section; no steps or criteria |
| Expand dimensions, filters, overrides, case cap | Host | One implementation, `dokime-domain` |
| `materialize(parameters)` | Plugin | Pure; the host may call it for preview and validation |
| `Execution`, ordering, retries, cancel, verdict | Host | The execution manager |
| Step, criterion, initialize, cleanup bodies | Plugin | Ordinary operations |

## Plugins

```rust
pub enum Plugin {
    Managed(ManagedPlugin),   // bundle: installed, started, supervised by Dokime
    Remote(RemotePlugin),     // URL: the user runs it; Dokime connects
}
```

The variant decides only how the channel is obtained and who owns the
process. Nothing above it branches on the variant.

| | Entry Is | Removed By | States |
| --- | --- | --- | --- |
| Managed | An installed bundle | Uninstalling it | Starting, ready, failed |
| Remote | A URL | Removing it from the list | Connecting, ready, unavailable |

An entry exists until someone removes it; availability is a state. Adding and
removing a remote plugin are Public operations, so the settings page and a
script use the same path.

## The Test Case

```proto
syntax = "proto3";
package dokime.v1;

message Metadata {
  string identifier = 1;
  string label = 2;
  string description = 3;
}

message TestCase {
  string template = 1;
  string plugin = 2;                  // plugin id
  bytes digest = 3;                   // catalog digest it was materialized from
  map<string, Value> parameters = 4;  // resolved
  repeated Step steps = 5;
  repeated Criterion criteria = 6;
  repeated string streams = 7;        // execution streams the host opens
}

message Step {
  Metadata metadata = 1;              // evidence keys on metadata.identifier
  string operation = 2;               // generated by the SDK, Host visibility
}

message Criterion {
  Metadata metadata = 1;
  string operation = 2;               // generated by the SDK, Host visibility
}
```

- Generated operation names only need to be stable within one catalog digest.
  The host materializes again when the digest changed before execution.
- A step's retry count is its operation's retry policy.
- `<template>.materialize`, `<template>.initialize` and `<template>.cleanup`
  have stable identifiers. The last two are optional.

## Execution

```text
host: open the test case's streams
host: <template>.initialize(execution, parameters)
host: for each step: invoke step.operation          (retries per its policy)
host: for each criterion: invoke criterion.operation → verdict
host: <template>.cleanup(execution)                 (always, also after failure or cancel)
host: close the streams, fold verdicts, finalize storage
```

- All criteria must pass. A criterion that needs "either" reads several
  streams itself.
- Interactive Next, Run Step and Finish are decisions inside the host loop.
- Cancel is an ordinary operation cancel.
- The SDK keeps one suite instance per execution, created by the first call
  and dropped after cleanup. It is never serialized.

| On reconnect, `started_at` is | Result |
| --- | --- |
| Unchanged | The step in flight failed; retry it if its policy allows |
| Changed | Seal the execution and its cycles |

## Authoring

```python
import dokime


@dokime.suite("thermal.cycle", label="Thermal Cycle")
class ThermalCycle:
    def initialize(self, ctx):
        self.limit = ctx.parameters["limit"]
        self.chamber = ctx.operation(OpenChamber())

    @dokime.stream("Chamber Temperature [°C]", identifier="chamber.temperature")
    @dokime.observer(interval_ms=1000)
    def temperature(self, ctx) -> float:
        return self.chamber.read()

    @dokime.step("Ramp to Target", retries=2)
    def ramp(self, ctx):
        ctx.operation(SetTemperature(self.limit))

    @dokime.step("Hold")
    def hold(self, ctx):
        answer = ctx.prompt("Door closed?", choices=["Yes", "No"])
        ctx.record("door.check", closed=answer == "Yes")

    @dokime.criterion("Temperature Within Limit")
    def within_limit(self, ctx) -> bool:
        stats = ctx.statistics("chamber.temperature", step="hold")
        door = ctx.records("door.check").last()
        return stats.max <= self.limit and door.closed

    def cleanup(self, ctx):
        ctx.operation(CloseChamber())
```

```rust
#[dokime::criterion("Temperature Within Limit")]
async fn within_limit(&self, ctx: &Context) -> Result<bool> {
    let stats = ctx.statistics("chamber.temperature").step("hold").await?;
    Ok(stats.max <= self.limit)
}
```

- Steps and criteria have one fixed signature in every language: the
  instance and `ctx`.
- The SDK derives `materialize` from the decorated steps, criteria and
  streams. An author overrides it only when they depend on parameters:

```python
    @dokime.materialize
    def materialize(cls, case, parameters):
        for channel in parameters["channels"]:
            case.step(f"Measure Channel {channel}", cls.measure, channel=channel)
```

## Host Operations for Plugins

Called through `ctx`; each is a Public `dokime.v1` operation the plugin
declares as a requirement. The SDK methods are thin conveniences over
`ctx.operation`.

| `ctx` | Purpose |
| --- | --- |
| `prompt(...)` | Ask the operator and wait for the answer |
| `secret(identifier)` | Read Secret Storage |
| `settings()` | Read the plugin's settings |
| `record(kind, ...)` | Publish a record; returns once the host stored it |
| `records(kind)` | Read the execution's records of a kind (`count`, `last`) |
| `statistics(stream, step=None)` | Statistics of a stream so far, optionally for one step |
| `artifact(...)`, file capture, effects | As today's host operations |
| `progress(...)`, `log(...)`, traceability, document parts | New small operations replacing evidence-page fields |

```proto
message Statistics {
  uint64 count = 1;
  double min = 2;
  double max = 3;
  double mean = 4;
  double stddev = 5;
  double median = 6;
  double p05 = 7;
  double p95 = 8;
  double p99 = 9;
  double first = 10;
  double last = 11;
}
```

The host computes statistics once per stream and time range and serves every
criterion from that. Queries are scoped to the execution through `ctx`, and
the host records which data each criterion read.

## Streams, Observers and Records

| Declared In | Opened | Closed |
| --- | --- | --- |
| The catalog (plugin-wide, such as host telemetry) | When the plugin connects | When it disconnects |
| The `TestCase` (belongs to an execution) | Before `initialize` | After `cleanup` |

- The plugin sends one sample per message; the host stamps arrival and
  ingests it. Samples lost during a disconnect are accepted.
- An observer is a function and an interval; the SDK runs the timer and sends
  each value on the stream. A stream without an observer is a generator that
  yields samples when the device produces them.
- Records are not a stream. A verdict may rest on them, so each is an
  acknowledged host operation on the step's own call.
- Removed: stream leases, publication admission, sample and record delivery
  into a running template.

## Protocol Packages

| Package | Contents |
| --- | --- |
| `harmos.v1` | Plugin service, catalog, child calls, streams, failures |
| `dokime.v1` | Operations Dokime serves to clients and to plugins, and the messages for operations plugins serve (`TestCase`, `Step`, `Statistics`) |

Visibility and grants decide who may call an operation. "Automation" names
the activity of driving Dokime, not a package. The protos are attached to
every release; a breaking change moves the package to `v2`.

## SDKs

| Half | Uses | Built On |
| --- | --- | --- |
| Plugin | `harmos.v1` transport, `dokime.v1` messages and host calls | The Harmos SDK for the language |
| Client | `dokime.v1` services | Generated stubs plus a thin hand-written layer |

```python
# main.py
import dokime
from suite import ThermalCycle

async with dokime.serve(ThermalCycle, address="127.0.0.1:7001") as plugin:
    async with dokime.connect("bench.dokime-remote") as client:
        await client.plugins.add(plugin.url)
        cases = await client.templates.materialize("thermal.cycle", parameters={"limit": [70, 85]})
        cycle = await client.cycles.start(cases)
        async for progress in cycle.watch():
            print(progress)
```

- Every Public operation with a binding appears in every language's client
  through generation; a check keeps the stubs in step with the protos.
- Rust's client half is `dokime-client`, already used by the CLI and the
  desktop.
- Python is a pure Python package over `grpcio`: one wheel, no native build,
  `Remote` only. It does not start Dokime.
- Authoring parity across languages and between sidecar and guest is a soft
  target.

## What It Removes

Sizes are of existing paths, not deletion totals; several files are mixed.

| Area | Path | Lines |
| --- | --- | --- |
| Run and signal serving, plugin walker, evidence pump | `crates/dokime-runtime/src/execution/{serving,run,template,unwind}.rs`, `execution/workflow/`, `transport/`, `domains/execution/run/` | about 10,000 |
| Execution hand-off | `ExecutionFixture`, `ProviderExecutorRegistry`, `ExecutionProviderTarget`, provider outcome projections | part of `domains/execution/provider*` |
| Embedded plugins | `crates/dokime-runtime/src/runtime/embedded.rs` and its registration | about 1,200 with tests |
| PyO3 SDK, Python backend, stubs, wheel tasks | `sdk/python/src/`, `sdk/python/python/`, `sdk/python/tests/`, `tools/python/src/dokime_tools/{build,test}/` | about 24,500 |
| Leases, sample and record delivery, replay | `domains/telemetry/leases.rs`, `domains/execution/run/replay.rs` | mixed |
| Tests tied to the old loop | `crates/dokime-runtime/tests/integration/execution/workflow/` | about 6,300 |

Kept and renamed as the execution manager: durable admission and queueing,
the running transition, verdict folding, storage finalization, report intents
and cycle accounting (`transactions/provider*`, `provider_finish`).

Kept for managed plugins: install, store, bundles, feeds and installer
entries.

## Open Points

Not yet decided with the owner; each is settled before its task starts.

1. The fixed percentile set in `Statistics` (proposed: 5, 95, 99 and the
   median).
2. Whether a Wasm guest can be a managed Dokime plugin in the first version.
3. How settings changes reach a running plugin.
4. The sample rates of existing plugins, to confirm one sample per message is
   enough for each.
5. Reconciling the overlapping changes named in the proposal, including which
   of them this change absorbs.
6. Spec deltas that retire `python-backend`, `python-sdk`,
   `python-plugin-authoring` and the reload and start-order requirements this
   change removes.
