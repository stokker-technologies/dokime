# Organization Packs Design

## Organization Pack Extension

Replace authored branding/brand.toml and branding-pack surfaces with organization/organization.toml and Organization Pack naming. Preserve appearance, pending restart activation, compiled defaults, OS bundle/storage identity and deep-link registration. Existing installed pack data is retained through validated migration or explicit import guidance, never silently deleted. Organization configuration supplies defaults, not enforced administrator policy; secret values never travel in packs.

One resolved update policy owns disabled/manual/automatic-check behavior and selected named source. Sources support direct Tauri updater manifests and GitHub/GitLab Releases; checks may be automatic but installation is always explicit. Named GitLab host/project/OAuth settings support different remotes. Credentials are scoped to host, account and OAuth client; each initial API/manifest/download URL independently selects credentials and redirects cannot forward them across origins. Source selection never changes compiled signing trust. Invalid policy input preserves last valid configuration and surfaces an error instead of silently falling back to public endpoints.

Source inventory: authored assets and Python branding generator; GUI native app/branding.rs and gitlab.rs, startup and command catalog; desktop branding/update adapters and Settings; domain plugin metadata, runtime install/consent/restart and release asset manifests; build/package paths, examples, README and generated guidance. The integration owner writes the remaining organization, updater and Secret Storage cutover, owns all Git adoption and generated bindings, and makes no further agent dispatches under the replacement guidance. Existing workers retain their completed source and assigned handoffs. No additional branch, chat or worktree is created. Organization packs carry no plugin secret-reference or binding declarations; authentication state stays local.

Plugin release discovery uses a bounded version-1 JSON manifest with `package`, SemVer `version`, SemVer requirement `requires_dokime` and `assets`, each containing `target`, HTTPS `url` and SHA-256 `sha256`. Package means inspected bundle identity, never an executable owner. Select against the connected backend's version and authoritative Rust target, adding target to BackendIdentity and its server/fixture/client producers. Reject duplicate targets, mismatched inspected package/version or digest before presenting existing consent; reuse bundle inspection and native-sidecar admission rather than duplicating them. Discovery does not grant install consent or create plugin self-update ownership. Provider sources resolve this manifest as `plugins.json`; direct sources name its URL. No new plugin-signing authority is implied by feed integrity.

## Source Order

Replace Organization Pack assets/generation/loading and lock its pure manifest/policy contracts. Replace the obsolete GitLab-only account/updater flow with origin-scoped authentication, provider resolution and exact-candidate verification/install; plugin releases stage through the existing host lifecycle.
